# 決定事項と要件

最終更新: 2026-09-14

## 1. 目的と確定方針

- プロジェクト名: MushagaeshiBinDiff。
- 配置先: ~/Github/musha-bin-editor（2026-09-14に旧MushagaeshiBinDiffから移動）。
- GitHubリポジトリー: https://github.com/hirofumi-iwasaki/musha-bin-editor 。既存のmainブランチを使用。アプリ表示名はMushagaeshi Bin Diffを維持。
- 2つのバイナリーファイルを比較表示し、差分箇所を色替えで示すバイナリーエディターを開発する。
- オープンソースソフトウェアとして、最終的にGitHubへ公開する。
- 公開ライセンスはGNU GPLv3。直前の推奨に沿い、表記はGPL-3.0-or-later（第3版またはそれ以降）とする。詳細は[ライセンス方針](LICENSE_POLICY.md)を参照。
- 開発基盤はFlutter／Dartを採用する。
- 当面はmacOSのみで動作すればよい。MacはApple Silicon（M1以降）を対象とし、Intel Mac対応は要求しない。
- 将来Windows／Linuxにも展開できる設計とする。iOS／iPadOS／Androidは将来の検討対象であり、初期リリースの要件ではない。
- 原則としてサポート中のOSを対象にする。ただしサポート中の全OSを網羅する約束ではない。
- 今後の作業方針と進捗は.chatgptに集約する。

## 2. 採用した初期版の設計方針

2026-09-13、ユーザーの「その方針でまずは良いかなと思います」という回答により、[詳細設計](DESIGN.md)を初期開発の基準として採用した。以下を決定事項とし、設計内の暫定数値や実機検証事項は引き続き調整対象とする。

### 画面・比較

- アプリ表示名はMushagaeshi Bin Diff。初期版は1ウィンドウ・1比較セッションとする。
- 左右にオフセット、16進数、ASCIIを表示する。既定は16バイト/行、左右共通で8バイト/行にも切り替えられる設計とする。
- ASCIIは0x20〜0x7Eを表示し、それ以外は「.」。初期版では文字欄からの編集は行わない。
- 同じ絶対オフセットのバイト同士を比較し、不一致バイトのHEX背景を赤系で強調する。
- サイズが異なる場合、片側にしかない末尾は橙系、欠損側は編集不能の「--」とする。
- 差分、未比較、選択、キャレット、未保存編集を区別する。ダークモードと色だけに依存しない状態表示を設計する。
- 左右同期スクロール、前/次の差分区間への移動、オフセット指定移動を用意する。
- 比較には現在の編集内容を反映する。挿入による位置ずれは初期版で補正せず、「同一位置比較」であることを表示する。

### 編集・保存

- 左右とも編集可能とし、ファイルを開いた直後は閲覧モード。各側で明示的に編集を有効にする。
- 初期版はファイルサイズを変えない上書き編集。挿入・削除は後続とする。
- HEX2桁で1バイトを確定し、バイト単位/範囲選択、HEXコピー/貼り付けを用意する。不正入力やEOFを越える貼り付けは部分適用しない。
- Undo/Redoは左右の文書ごとに管理し、未保存状態を表示する。保存後もUndoを残す。
- 同じ実体のファイルを左右に開いた場合は文書を共有し、編集も同期することを表示する。
- 別名保存を先に実装し、安全な置換と外部変更検出の検証後、初期実用版で元ファイルへの上書き保存を追加する。
- 編集開始時に基底データの作業用スナップショットを確保する。保存は一時ファイルへの書出し後に置換し、失敗時に元ファイルや未保存編集を失わない手順とする。
- 未保存状態で閉じる・ファイル差替え・終了する場合は保存/破棄/キャンセルを扱う。

### 内部構成・開発順

- Flutter/Dartの単一プロジェクト内で、中核、ファイルI/O、画面、アプリ操作、OS連携の責務を分ける。中核はFlutterと直接のファイルI/Oに依存させない。
- 範囲読み込み、上限付きキャッシュ、表示範囲中心の描画を採用する。比較等の重い処理はIsolateで画面操作から分離する。
- 編集の世代管理により古い比較結果を破棄する。差分索引と編集履歴にも容量上限を設ける。
- 開発環境確認 → 左右表示/差分の試作 → 編集/Undo/別名保存 → 安全な上書き保存 → 性能・操作性検証 → OSS公開準備の順に進める。
- 位置合わせ比較、挿入削除編集、検索、左右範囲転送、複数ウィンドウ、USB制御は後続とする。

### 対応OS・性能・実装判断（2026-09-13確定）

- 初期対応OSはmacOS 26 Tahoeと、その1世代前のmacOS 15 Sequoia。各OSの最新更新適用環境を対象とする。最低対応OSはmacOS 15。
- 対象ハードウェアはM1以降のApple Silicon Macで、対象OSを実行できる機種。Intel Macは対象外。
- 上記2世代を今回の固定対象とし、新OS登場時に自動で対応範囲を変更しない。追加・最低OS変更は検証後に扱う。
- 性能は「ほどほどで良い」というユーザー方針を採用。通常の閲覧・編集が実用的に操作でき、比較中も画面操作やキャンセルができることを重視する。
- 厳密な処理速度・FPS・最大容量の保証値を先に設けない。設計書の容量・キャッシュ値は評価用の目安として扱い、過度な最適化より正確さ・データ保全・保守性を優先する。
- その他の実装判断は既存の方針書・詳細設計に従って進める。SDKや内部構成の通常の選択は開発側で判断し、対応OSや機能範囲を変える必要が生じた場合に相談する。


## 3. 将来のOS対応方針

macOS限定で開始するという最新方針を優先する。以下は過去に検討した拡張候補であり、現時点の動作保証ではない。

- Windows: Windows 11 x64。会話時点の最低候補は25H2。導入時にライフサイクルを再確認する。
- Linux: Ubuntu Desktopの直近2世代のLTS、x86-64、標準GNOME。会話時点では24.04／26.04 LTS。Waylandセッションで検証する。
- Windows ARM64、Debian、Linux ARM64等は検証体制を確保してから検討する。
- macOS: 初期対象は26と15で確定。将来の更新は最新正式版と1つ前を基本候補に検討する。Appleによる固定年数のサポート保証を意味しない。
- 新OSは動作検証後に正式対応へ追加する。
- OSと採用フレームワーク双方の対応範囲を確認する。
- 最低OSの変更は事前告知する運用を想定する。

## 4. 2番目のアプリとの関係

将来、TL866CSやGQ-4X4などのUSB ICプログラマーに対し、読み取り・書き込み・検証・テストを行う別アプリを構想している。

- 本プロジェクトのバイナリー処理と16進数表示部品を再利用できるようにする。
- 本プロジェクトにUSB機器制御を最初から組み込む必要はない。
- TL866CSはminipro連携が有力候補。最初は外部プログラム連携を検討する。
- GQ-4X4は公開SDK／プロトコル／既存実装の調査と実機検証が必要。対応を確約しない。
- USBアプリのモバイル対応は別途検討する。FlutterのOS対応だけでUSB機器が制御できるとは扱わない。
