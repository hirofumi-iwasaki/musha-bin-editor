# Mushaaeshi Binary Editor 詳細設計

作成日: 2026-09-13
状態: 2026-09-13にユーザーが初期開発の方針として採用。決定事項はDECISIONS.mdに集約。性能目標・容量等の暫定数値と実機検証事項は未確定であり、実装・評価で調整する。
対象: macOS 26 Tahoe / macOS 15 Sequoia、M1以降のApple Silicon（対象OSを実行できる機種）。FlutterでUI、Dartで中核処理を実装する。

## 1. 目指す使い方

2つのバイナリーファイルを左右で比較し、不一致バイトを見つけ、その場で上書き編集して保存する。WinMergeの左右比較を操作上の参考とし、BzEditorのような16進数エディターを目指す。両製品の機能互換やコード流用を前提としない。

初期版は1ウィンドウ・1比較セッション。タブ、複数ウィンドウ、USB制御は後続。片側だけ開いた状態でも閲覧・編集できる。

## 2. 初期版の範囲

| 項目 | 推奨仕様 |
| --- | --- |
| 開く | 左右それぞれファイル選択。片側へのドラッグ＆ドロップは使い勝手改善段階 |
| 表示 | オフセット、16進数、ASCII。既定16バイト/行、8バイト単位に余白 |
| 比較 | 同じ絶対オフセットのバイトを比較。差分背景と前後の差分移動 |
| スクロール | 左右同期。行幅は両側で共通。狭い画面は共通で8バイト/行へ切替可能 |
| 編集 | 左右とも可能。開いた直後は閲覧モードで、各ペインの「編集」を明示的にオン |
| 操作 | バイト選択、範囲選択、HEXコピー/貼り付け、オフセット指定移動 |
| 履歴 | 左右独立のUndo/Redo。操作対象はフォーカス中のペイン |
| 保存 | 別名保存を先に実装。安全な置換・外部変更検出の確認後、初期実用版で上書き保存 |
| 後続 | HEX検索、左右の範囲転送、差分一覧/全体マップ、挿入削除編集、位置合わせ比較 |

ASCIIは0x20〜0x7Eをそのまま表示し、それ以外は「.」。初期版は文字欄からの編集・多バイト文字コード表示を行わない。文字欄クリックは対応バイトを選択する。

## 3. 画面と表示規則

概略（実装画面ではなく構造案）:

    Mushaaeshi Binary Editor
    [左を開く] [右を開く]  [前の差分] [次の差分] [移動]
    ┌ 左: original.bin    [編集 OFF] ┬ 右: modified.bin * [編集 ON] ┐
    │ offset  HEX            ASCII │ offset  HEX            ASCII │
    │ 00000000  00 01 02 ...  ...   │ 00000000  00 FF 02 ...  ...   │
    │ 00000010  ...                │ 00000010  ...                │
    └──────────────────────────────┴──────────────────────────────┘
    同一位置比較 | 差分 12バイト / 3区間 | 右: 0x00000001 | 比較完了

- オフセットは0始まり。最低8桁、サイズに応じて桁数を増やす。左右の列幅は揃える。
- 不一致のHEX 2桁の背景だけを淡い赤にし、行全体は塗らない。ASCII側にも対応位置を示す。
- 相手側にバイトが存在しない末尾は、存在する側を橙色、存在しない側を「--」とする。「--」は0x00ではなく編集不能な空欄。
- 未比較領域は通常の一致表示と区別し、薄いマーカーと「未比較」を表示する。
- 選択は青い枠/半透明色、キャレットは高コントラスト枠、編集済みは下線とファイル名の「*」。差分色を選択色だけで消さない。
- ダークモードの配色を用意し、色以外にもステータスとアクセシビリティの読み上げで状態を伝える。
- 両方未選択・片側のみ・読込中・比較中・比較中断・完了・エラーを明確に区別する。比較中は確定した差分数を「検出済み」と表示する。
- 右側の縦スクロールバーとホイール操作で共通の先頭オフセットを移動。短い側のEOF後も長い側に合わせて空欄を表示する。

## 4. 差分の定義

共通範囲[0, min(左サイズ, 右サイズ))を直接比較する。値が違えばmodified。共通範囲を超えて左だけに存在すればleftOnly、右だけならrightOnly。両方存在して等しければequal。未処理はunknown、読込失敗はerrorとして区別する。

差分バイト数はmodified + leftOnly + rightOnlyの位置数。左右で二重計上しない。連続する不一致を1差分区間として前後移動の単位にし、一致を挟むと別区間とする。内部の型付き区間は種別が変われば分割してよいが、ナビゲーション時は隣接区間をまとめる。

例: 左が「10 20 30」、右が「10 FF 20 30」なら、初期版はオフセット1・2・3の3位置が差分になる。挿入を推定して並べ直さない。画面に常時「同一位置比較」と表示する。

前後移動は現在区間を飛ばして次/前の区間先頭へ移動する。末尾からの自動循環はせず「最後の差分」。比較途中は未走査の先を「差分なし」と断定せず、走査中であることを表示する。

編集対象はメモリー上の現在の文書内容。ディスク上の元ファイルだけを比較しない。編集により相手側と同じになれば赤背景が消えるが、未保存の下線は残る。

## 5. 編集・選択・Undo/Redo

- バイト単位のキャレットと半開区間[start, end)の選択を使う。内部オフセットは整数で保持する。
- HEX入力は2桁で1バイト確定。1桁目は入力プレビューとし、2桁目で編集履歴へ登録。Escでプレビュー取消。移動・フォーカス変更では未完の1桁を取消し、保存前にも取消した旨を通知する。
- 矢印で1バイト/1行、Shiftで選択拡張、Page Up/Downで表示単位移動。Tabでペインを移る。主要操作はmacOSメニューにも用意する。
- Cmd+Cは「00 A1 FF」形式のHEXテキスト。貼り付けは空白・改行を許容し、それ以外はHEX 2桁列のみ。奇数桁・不正文字は全体を拒否し、部分適用しない。
- 選択ありの貼り付けは選択バイト数と一致する場合のみ許可。選択なしはキャレット位置から上書き。EOFを越える貼り付けは全体を拒否する。
- 初期版ではサイズは不変。Insert/Deleteによるバイト追加削除は提供しない。空ファイルは表示できるが、初期版では内容を作成できない。
- Undoは原則1バイト入力、貼り付けは1操作。保存後もUndoを残し、保存済み状態との差で未保存を判定する。履歴位置だけに頼る場合も分岐を識別し、保存点消失を扱う。
- 編集差分とUndo履歴はメモリー上限を設ける。上限到達時は編集を拒否して理由を示し、黙って履歴を破棄しない。大量編集対応は一時ファイル退避を追加して拡張する。
- 閲覧ロックはアプリ内の編集防止であり、ファイルシステムの権限とは別。元ファイルが書込不可でも別名保存できる設計とする。

## 6. 内部構成

初期段階は1つのFlutterプロジェクトで分離する。追加の状態管理ライブラリは必要性が出てから決める。

    lib/
      core/          # ByteRange、Document、EditCommand、比較規則
      application/   # CompareSession、操作、進捗、状態遷移
      infrastructure/# 範囲I/O、キャッシュ、一時ファイル、安全な保存
      presentation/  # ウィンドウ、HexPane、描画、入力、アクセシビリティ
      platform/      # macOSメニュー、ダイアログ、必要なOS固有処理

coreはFlutterとdart:ioに依存しない。抽象ByteSourceを通じた範囲読み取りで、将来USB読出しバッファも同じ表示部品へ渡せる。USB通信自体は持ち込まない。

主なモデル:

| モデル | 保持する内容 |
| --- | --- |
| BinaryDocument | 文書ID、サイズ、基底データ参照、編集オーバーレイ、revision、保存点 |
| EditCommand | 開始位置、変更前/後バイト列。左右それぞれの履歴に格納 |
| CompareSession | 左右の文書ID、比較方式、世代番号、比較済み領域、進捗 |
| DiffPage | 対象ブロック、差分ビット列または区間、件数、左右revision |
| HexViewport | 先頭行、行内スクロール量、bytesPerRow、選択、キャレット |
| FileIdentity | 正規化パス、取得可能ならファイル識別子、サイズ、更新情報 |

同じ実体のファイルを左右に開いた場合は文書モデルを共有し、片側の編集は両側に反映する。「同じファイルのため編集も同期」と表示する。独立した比較をしたい場合はコピーを開く。保存先が別の開いている文書と衝突する場合は通常保存を止め、別名保存へ誘導する。シンボリックリンク・ハードリンクも可能な範囲で識別する。

## 7. 大容量処理と非同期整合性

全体を文字列化せず範囲読み取りする。初期調整値はI/Oブロック1MiB、表示用キャッシュ左右合計64MiB、編集+履歴予算128MiB。これらは性能保証ではなく測定で調整する値。

HexPaneは表示中の行と少量の前後行だけをCustomPainter/TextPainterで描く。1バイト1Widgetにはしない。全ファイル長を巨大なスクロールピクセルへ直接変換せず、整数の先頭行と局所ピクセル量で管理する。スクロールバーは全体への比率移動、正確な移動はオフセット指定を使う。

データ処理を担当する長寿命Isolateにファイルハンドル、編集状態、比較キャッシュの所有を集める案を基本とする。UIは描画範囲と小さな編集要求を送り、表示用バイトと差分だけを受け取る。比較は短いブロック単位に区切り、入力・表示読込を優先し、ブロック間でキャンセルや編集要求を処理する。保存I/O中もUIのイベントループを止めない。

比較結果にはセッション世代と左右revisionを付与し、UIは古い結果を破棄する。編集したブロックと隣接区間を無効化し再比較する。キャレットのある表示範囲を先に比較し、全体走査を続ける。ファイル再選択、閉じる、再読込時は世代を進めて残りをキャンセルする。

差分の保存量にも上限を設ける。1バイトおきに異なるファイルで巨大な区間オブジェクト配列を作らない。ブロックごとの件数・先頭/末尾状態を小さな索引に保持し、詳細はビット列とLRUキャッシュで保持する。キャッシュ外の前後移動は必要ブロックを再読込/再比較する。全体走査後の区間数はブロック境界の連続差分を結合して集計する。

## 8. 保存と外部変更

通常保存も別名保存も、保存開始時の確定済みrevisionを保存する。初期実装では保存中の対象文書への編集を一時停止し、閲覧は可能にする。

1. 未完HEX入力を解消し、対象文書・保存先を確定する。
2. 元ファイルと保存先の外部変更・同一実体・権限を検査する。
3. 保存先と同じディレクトリーに一時ファイルを作る。
4. 基底データに編集を重ね、一定サイズで順次書き出す。
5. 書き込み・flush・closeの成功とサイズを確認する。
6. 置換直前に外部変更を再検査し、OSに合わせた置換処理を行う。
7. 成功後のみ保存済み状態へ移行し、新しい基底データとハンドルに切り替える。

基底切替後もUndo用の変更前後バイトを保持する。保存済み状態からUndoした場合は、保存後の基底に対する新しいオーバーレイを作る。別名保存成功後はその文書のパスを新しい保存先へ変更する。

空き容量不足、権限不足、書込/置換失敗では編集を保持し、元ファイルを先に削除しない。置換まで到達しなければ一時ファイルを安全に後始末する。成功不明の場合は保存済み扱いにせず状況を伝える。パーミッションや拡張属性の保存方針、シンボリックリンク先への保存、クラッシュ/電源断時の耐久性は実機検証事項とし、単純なrenameで全て保証できるとは扱わない。

外部変更はファイル監視に加え、アプリ復帰・保存前の識別情報検査で補う。変更が検出された文書は基底データが古い状態として比較を無効化し、通常保存を止める。未保存編集がなければ再読込、あれば破棄して再読込するか既存の基底が保全されている場合に別名保存する。範囲読み取りだけでは任意の外部書換えから元内容を復元できないため、編集開始時に基底の作業用スナップショットを一時ファイルに確保する案を採用する。

スナップショット作成はバックグラウンドで実施し、完了までは閲覧専用。作成前後に元ファイルを再検査するが、同時書換えの完全検出を保証しない。OSのクローン機能は最適化候補、まずはストリームコピーで正しさを確立する。一時領域不足時は編集開始を中止する。表示・比較用読込にも前後検査を適用し、変化検出時は再開を要求する。

未保存状態で閉じる/ファイル差替え/終了する際は「保存・破棄・キャンセル」。左右の変更文書をそれぞれ扱い、保存失敗・キャンセル時に終了しない。自動クラッシュ復旧は初期版の範囲外。

## 9. 拡張設計

位置合わせ比較はOffsetCompareとは別のAlignedCompareとして追加する。左オフセット・右オフセット・長さ・種別を持つ対応区間を出力し、表示行と実ファイル位置の対応表を作る。初期から常に左右のオフセットが同じだとUI全体に埋め込まない。

大容量の位置合わせはブロックの一致候補を探して局所的に精密比較する方式を評価する。反復バイト列の曖昧さ、メモリー上限、タイムアウト、同一位置比較へのフォールバックを別途設計する。挿入削除編集は別課題であり、その段階でpiece table等を比較評価する。

左右の範囲転送は、初期の上書き方式では同じ長さの実在範囲に限定し、1回のUndo可能操作にする。欠損側へ長さを増やす転送は挿入削除編集の導入後に扱う。

## 10. 検証計画・実装順

### A. 最小表示試作

Flutter/Xcode環境を確認し、macOS 15/26に対応するSDKを固定する。左右表示、範囲読込、差分、同期スクロール、オフセット移動を実装。ここでCustomPainterの文字品質、選択、VoiceOverの試作を行う。VoiceOverには操作中のバイト・オフセット・値・差分状態を提供し、全バイトを一度にSemanticsへ展開しない。

### B. 編集とデータ保全

編集用スナップショット、上書き編集、左右独立のUndo/Redo、HEX貼り付け、別名保存を実装。その後、外部変更検出と安全な上書き保存を実装し、未保存で閉じる操作まで検証する。

### C. 実用評価と公開準備

差分ナビゲーションの大容量性能、キーボード操作、ダークモード、ファイル名、エラー表示を調整。ライセンスはGPL-3.0-or-laterとする（LICENSE_POLICY.md参照）。配布、署名・公証は別途確定する。

正しさの検証ケース:

- 同一、1バイト差分、連続差分、1バイトおきの差分、全バイト差分。
- 両方空、片方空、サイズ違い、最終バイト、行境界、I/Oブロック境界。
- 編集で一致する、Undoで再び差分になる、保存後Undo、Redo分岐、左右での独立操作。
- 不正HEX、奇数桁、EOFを越える貼り付け、未完入力で保存。
- 比較中の編集/再選択/キャンセルで古い結果が描画されない。
- 保存結果が期待バイト列と完全一致する。書込失敗/置換失敗時に元ファイルと編集内容を保つ。
- 外部変更、同一ファイル、別名経由の同一実体、保存先衝突、スナップショット作成失敗。

性能方針は「ほどほどで良い」。正確な比較・保存と、通常の閲覧・編集で操作を妨げない応答性を優先し、厳密な速度・FPS・容量保証は設けない。1MiB/100MiB/1GiBを評価用の候補とし、10GiBは必要性が生じた場合の追加確認とする。従来案の初画面1秒・60fps・1GiB実用目標は必須の合格基準としない。キャッシュや履歴の数値は内部調整値として実測で見直す。比較・編集用コピー中も進捗とキャンセルを扱う。実測時はOS/SDK/ハードウェア/ビルド方式を記録する。

## Adopted UI refinements — 2026-09-14

English is now the sole application language. The additional content title/banner and Open Sample action are removed; the native macOS title bar identifies the app. Wheel and pan/zoom trackpad input over either binary pane must update the shared vertical viewport, including when the pane overflows horizontally. The `.app` artifact is packaged into `dist/` for direct Finder launch.

Vertical input is handled by Flutter's standard `ScrollPosition`, using the macOS-provided delta and direction unchanged. Each binary pane forwards only vertical pointer-scroll events past its nested horizontal viewport; Flutter handles trackpad drag physics and the scrollbar. The visible first row is derived from the standard pixel position.

The macOS window is a file-URL drag destination. It accepts exactly one regular file, determines left/right from the drop location, retains security-scoped read access under the existing read-only user-selected-file entitlement, and sends the path and side through the existing platform channel. Flutter opens the file through the same comparison controller path used by the file chooser. Each pane exposes an English accessibility drop-target label.

The effective AppKit drag destination is a dedicated root `NSView` that hosts the Flutter view controller, not the `NSWindow`. It forwards live drag coordinates in flipped view coordinates. Flutter performs final hit-testing against the actual rendered pane bounds, so both the pane header and hexadecimal body are accepted while toolbar/status-bar drops are rejected. The active pane receives a visible highlight during the drag.
